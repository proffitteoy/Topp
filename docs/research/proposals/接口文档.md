> 状态：historical proposal。本文保留当时的 Tide 临时代号和讨论过程；已实现的 Topp v0.1.0 契约以 `docs/API.md` 为准。

你的库首发接口不要多。对 Tide 这种“高性能 persistence diagram distance kernel”，我建议把正式公共 API 控制在：

**6 个核心函数 + 1 个核心对象 + 少量元信息接口。**

内部那些 `CandidateStrategy / MatcherStrategy / GraphStrategy / ComponentStrategy` 全部不要进入普通 Python API。

下面用 `tide` 作为临时代号，不代表最终 PyPI 包名。

---

## 1. 顶层公共 API 应该长这样

```python
from tide import (
    PreparedDiagram,
    prepare_diagram,

    bottleneck_distance,
    bottleneck_distances,
    bottleneck_within,

    wasserstein_distance,
    wasserstein_distances,
)
```

用户正常使用时，不应该需要知道 Hungarian、SAP、CSR、Hopcroft–Karp、AVX2、sweep、dispatcher 这些东西。

最简单使用：

```python
import numpy as np
import tide

X = np.array([
    [0.0, 1.0],
    [0.3, 0.8],
])

Y = np.array([
    [0.0, 1.1],
    [0.4, 0.9],
])

d = tide.bottleneck_distance(X, Y)

w = tide.wasserstein_distance(
    X,
    Y,
    order=2,
    internal_p=2,
)
```

这就是普通用户应该看到的复杂度。

# 2. `bottleneck_distance`

这是第一核心接口。

我建议签名：

```python
def bottleneck_distance(
    diagram_a,
    diagram_b,
    *,
    out=None,        # 实际上单值没必要，可以不要
) -> float:
    ...
```

实际上我更建议最终就是：

```python
def bottleneck_distance(
    diagram_a: DiagramLike | PreparedDiagram,
    diagram_b: DiagramLike | PreparedDiagram,
) -> float:
    ...
```

不要加：

```python
method=
solver=
candidate_strategy=
matcher=
epsilon=
dispatcher=
```

v0.1 首发是 exact，就直接 exact。

数学语义固定为

[
d_B(X,Y)
========

\inf_{\gamma}
\sup_{x\in X}
|x-\gamma(x)|_{\infty},
]

其中 diagonal 具有无限重数。

用户不关心内部到底用了：

```text
small-N bitset
medium adaptive
large geometric matching
quickselect
Hopcroft-Karp
mandatory flow
```

全部 dispatcher 自动决定。

# 3. `wasserstein_distance`

这是第二核心接口。

建议：

```python
def wasserstein_distance(
    diagram_a: DiagramLike | PreparedDiagram,
    diagram_b: DiagramLike | PreparedDiagram,
    *,
    order: float = 1.0,
    internal_p: float = np.inf,
) -> float:
    ...
```

这两个参数名字建议直接采用 TDA 领域比较成熟的术语：

* `order`：外层 Wasserstein order，即 (q)
* `internal_p`：点之间使用的 (L^p) metric

数学定义：

[
W_{q,p}(X,Y)
============

\left(
\inf_{\gamma}
\sum_{x\in X}
|x-\gamma(x)|_p^q
\right)^{1/q}.
]

你的 v0.1 当前只支持：

```python
order=1, internal_p=np.inf
```

也就是

[
W_{1,\infty},
]

以及：

```python
order=2, internal_p=2
```

即

[
W_{2,2}.
]

所以：

```python
tide.wasserstein_distance(
    X,
    Y,
    order=1,
    internal_p=np.inf,
)
```

正常。

```python
tide.wasserstein_distance(
    X,
    Y,
    order=2,
    internal_p=2,
)
```

正常。

但：

```python
tide.wasserstein_distance(
    X,
    Y,
    order=3,
    internal_p=2,
)
```

应该：

```text
NotImplementedError
```

而不是 `ValueError`。

原因是：

> (W_{3,2}) 在数学上完全合法，只是 Tide 当前没有实现。

这个区别最好从第一版就处理好。

# 4. Diagram 输入协议必须明确

这是发布库必须定义清楚的东西。

所有距离接口统一接受：

```python
shape == (n, 2)
```

例如：

```python
[
    [birth_1, death_1],
    [birth_2, death_2],
    ...
]
```

接受：

```python
numpy.ndarray
list[list[float]]
tuple
其他可转换为 NumPy array 的对象
```

例如：

```python
tide.bottleneck_distance(
    [[0, 1], [2, 4]],
    [[0, 1.2], [2.1, 4]],
)
```

应该正常工作。

内部统一转换为：

```python
float64
C-contiguous
(n, 2)
```

但是 NumPy 已经满足：

```python
dtype=float64
C-contiguous
shape=(n,2)
```

时应该走尽可能零拷贝的路径。

# 5. 输入合法性契约

这件事必须在首发前冻结。

我建议以下规则。

### 空图合法

```python
X = np.empty((0, 2))
```

必须合法。

比如：

```python
bottleneck_distance(empty, empty)
```

返回：

```python
0.0
```

---

### 对角点合法

```python
[1.0, 1.0]
```

合法。

虽然 persistence 为 0，但不要报错。

---

### 重复点合法

```python
[
    [0.0, 1.0],
    [0.0, 1.0],
    [0.0, 1.0],
]
```

必须保留 multiplicity。

不能自动 unique。

你的内部可以做重复点压缩优化，但数学意义必须保持重数。

---

### `NaN` 非法

```python
[0.0, np.nan]
```

直接：

```text
ValueError
```

不要让 `NaN` 跑进 C++ matcher。

---

### birth > death

例如：

```python
[2.0, 1.0]
```

我建议公共接口直接：

```text
ValueError
```

不要自动 swap。

因为自动：

```python
[2, 1] -> [1, 2]
```

属于悄悄修改用户数学数据，这很危险。

---

# 6. Essential points

这个需要专门定义。

Persistence diagram 里至少应该支持：

[
(b,+\infty).
]

如果你的数学设计决定支持 extended persistence，还可以支持其他 canonical infinity forms。

但公共 API 最好不要什么：

```python
(+inf, 1)
(1, -inf)
(+inf, +inf)
```

都莫名其妙接受。

我建议首发明确：

```python
finite birth, finite death
finite birth, +inf
```

是核心支持。

如果你确定当前 Bottleneck/Wasserstein 内核已经严格支持：

[
(-\infty,d),
\qquad
(-\infty,+\infty),
]

那么再公开。

重点不是支持得越多越好，而是：

> README 必须明确哪些 infinity combinations 有定义。

否则不同库之间会出现非常难查的结果差异。

# 7. `PreparedDiagram`

这是你的库非常重要的接口。

因为你已经专门做了：

* midpoint
* half persistence
* sorted birth
* sorted midpoint
* SoA
* prepared batch

如果 Python 不暴露 prepared diagram，这些优化价值会损失很多。

建议：

```python
prepared = tide.prepare_diagram(X)
```

返回：

```python
PreparedDiagram
```

然后：

```python
tide.bottleneck_distance(prepared, Y)
```

或者：

```python
tide.wasserstein_distance(
    prepared,
    Y,
    order=2,
    internal_p=2,
)
```

---

## `prepare_diagram`

签名：

```python
def prepare_diagram(
    diagram: DiagramLike,
) -> PreparedDiagram:
    ...
```

PreparedDiagram 必须是 immutable。

不要让：

```python
prepared.points[0, 0] = ...
```

修改内部缓存。

否则 midpoint、birth order、KD-tree 等缓存全部失效。

建议：

```python
class PreparedDiagram:
    @property
    def n_points(self) -> int:
        ...

    @property
    def n_finite_points(self) -> int:
        ...

    def __len__(self) -> int:
        ...
```

首发就够了。

不要暴露：

```python
finite_midpoint_order
half_persistence
soa_births
kd_tree
candidate_cache
```

这些属于 implementation detail。

---

# 8. PreparedDiagram 最重要的语义

例如：

```python
prepared = tide.prepare_diagram(X)

d1 = tide.bottleneck_distance(prepared, Y)
d2 = tide.bottleneck_distance(X, Y)
```

必须保证：

[
d_1=d_2.
]

至少达到你定义的 numerical tolerance。

Prepared 只是：

> cache / preprocessing object

绝对不能改变数学结果。

# 9. `bottleneck_distances`

这是 one-to-many。

我认为这个接口必须首发。

因为这是你和很多简单 wrapper 拉开差距的地方。

建议：

```python
def bottleneck_distances(
    query: DiagramLike | PreparedDiagram,
    diagrams: Sequence[DiagramLike | PreparedDiagram],
    *,
    out: np.ndarray | None = None,
) -> np.ndarray:
    ...
```

例如：

```python
query = tide.prepare_diagram(X)

distances = tide.bottleneck_distances(
    query,
    [Y1, Y2, Y3, Y4],
)
```

返回：

```python
array([
    0.13,
    0.21,
    0.08,
    0.31,
])
```

shape：

```python
(m,)
```

其中 (m) 是 targets 数量。

---

# 10. Batch 必须是真 native batch

不能写成：

```python
def bottleneck_distances(X, Ys):
    return np.array([
        bottleneck_distance(X, Y)
        for Y in Ys
    ])
```

这种接口形式一样，但完全浪费你 C++ batch 优化。

必须是：

```text
Python
  ↓
一次 binding call
  ↓
C++ batch
  ↓
workspace reuse
prepared query reuse
output buffer reuse
```

这才能体现 Tide。

---

# 11. `out=` 参数

batch 接口我很建议支持：

```python
out = np.empty(1000)

tide.bottleneck_distances(
    query,
    diagrams,
    out=out,
)
```

这样在大量重复运算中可以避免：

```text
allocate
free
allocate
free
...
```

要求：

```python
out.dtype == np.float64
out.shape == (len(diagrams),)
out.flags.writeable
```

不符合直接报错。

这个接口对普通用户不是必须，但对你的性能库非常合理。

# 12. `wasserstein_distances`

完全对应：

```python
def wasserstein_distances(
    query: DiagramLike | PreparedDiagram,
    diagrams: Sequence[DiagramLike | PreparedDiagram],
    *,
    order: float = 1.0,
    internal_p: float = np.inf,
    out: np.ndarray | None = None,
) -> np.ndarray:
    ...
```

例如：

```python
distances = tide.wasserstein_distances(
    prepared,
    diagrams,
    order=2,
    internal_p=2,
)
```

同样要求 native batch。

这部分你现在 Wasserstein C++ 还没完整补齐的话，应该在 Python binding 前补。

因为否则接口结构会出现：

```text
Bottleneck:
single
prepared
batch

Wasserstein:
single only
```

非常不整齐。

最好首发就是对称的。

# 13. `bottleneck_within`

这个接口我建议保留。

你的 C++ 已经有：

```cpp
bottleneck_within(...)
```

Python 可以直接：

```python
def bottleneck_within(
    diagram_a: DiagramLike | PreparedDiagram,
    diagram_b: DiagramLike | PreparedDiagram,
    threshold: float,
) -> bool:
    ...
```

语义：

[
d_B(X,Y)\le \tau.
]

例如：

```python
if tide.bottleneck_within(X, Y, 0.1):
    ...
```

它不是：

```python
bottleneck_distance(X,Y) <= 0.1
```

的 Python 包装。

而应该直接使用你的 threshold decision kernel。

这对：

```text
nearest neighbor
top-k
clustering
candidate pruning
threshold search
```

非常有用。

也是一个很有价值的算法 API。

---

# 14. threshold 参数规则

```python
threshold < 0
```

直接：

```text
ValueError
```

```python
threshold = np.inf
```

理论上可以接受。

例如：

```python
bottleneck_within(X, Y, np.inf)
```

只要 distance 是有限，就返回 True。

但如果 essential structures incompatible 导致距离 (+\infty)，就要按照数学定义处理。

---

# 15. 为什么暂时不要 `wasserstein_within`

除非你已经实现专门的 decision algorithm。

不要为了接口对称写：

```python
wasserstein_within(X, Y, t):
    return wasserstein_distance(X, Y) <= t
```

这种 API 没有性能意义。

以后如果真的有 efficient decision procedure 再加。

# 17. Many-to-many / pairwise API

这个我建议接口先设计好，但可以放 v0.2。

最后应该有：

```python
bottleneck_distance_matrix(
    diagrams_a,
    diagrams_b=None,
)
```

如果：

```python
diagrams_b is None
```

返回 symmetric：

[
D_{ij}=d_B(X_i,X_j).
]

例如：

```python
D = tide.bottleneck_distance_matrix(diagrams)
```

返回：

```python
shape == (n, n)
```

只计算：

[
\frac{n(n-1)}2
]

次而不是 (n^2)。

Wasserstein 同样：

```python
D = tide.wasserstein_distance_matrix(
    diagrams,
    order=2,
    internal_p=2,
)
```

但是这个不是首发必须项。

# 18. 不推荐设计成一个万能 `distance`

我不建议：

```python
tide.distance(
    X,
    Y,
    metric="wasserstein",
    order=2,
    p=2,
)
```

因为以后会越来越乱：

```python
metric=
order=
p=
epsilon=
threshold=
approximation=
```

你的领域本来就有两个清晰的数学对象。

直接：

```python
bottleneck_distance(...)
wasserstein_distance(...)
```

最好。

# 19. `method=` 不应该公开

这个非常关键。

不要：

```python
wasserstein_distance(
    X,
    Y,
    method="sparse_sap",
)
```

不要：

```python
bottleneck_distance(
    X,
    Y,
    matcher="hopcroft_karp",

```


```text

```

而不是：

```text
我要你怎么计算
```

算法选择全部：

```text

```

# 22. Python validation 做什么

比如：

```python
def bottleneck_distance(X, Y):
```

Python wrapper 做：


```text

```

所有真正计算：

```python

```

进入 C++ 后都应该：


# 24. PreparedDiagram 应该 thread-safe

如果：

```python
p = tide.prepare_diagram(X)
```

用户应该可以：

```python
thread1 -> distance(p, A)
thread2 -> distance(p, B)
thread3 -> distance(p, C)
```

同时使用。

因此 PreparedDiagram：

```text
immutable
read-only
no shared mutable workspace
```

solver workspace 必须：

```text
per call
thread local
或独立对象
```

不能藏一个：

```cpp
mutable std::vector<double> workspace_;
```

然后多个线程一起写。


# 33. 不要公开 SolverStats

你现在 C++ 有很多：

```text
threshold_decisions
adjacency_checks
component_count
kd_nodes_visited
candidate_pairs
graph_bytes
solver_time_ns
...
```

普通用户：

```python
bottleneck_distance(X, Y)
```

绝对不应该返回：

```python
(distance, stats)
```

否则公共 API 被科研实验污染。

可以：

```python
tide._debug.bottleneck_stats(...)
```

或者：

```python
tide.bench
```

单独处理。

---

# 34. 不建议第一版加 `return_stats=True`

比如：

```python
bottleneck_distance(
    X,
    Y,
    return_stats=True,
)
```

看似方便，实际上以后 stats schema 会变成兼容包袱。

你会很快遇到：

```text
v0.1 stats 18 fields
v0.2 stats 25 fields
v0.3 algorithm changed
```

所以 stats 属于 unstable/debug。

---

# 35. 第一版也不要加 `workers=`

例如：

```python
bottleneck_distances(
    X,
    Ys,
    workers=8,
)
```

我建议先不加。

第一版：

```text
GIL released
native optimized sequential batch
```

就够。

以后真正设计好：

```text
OpenMP
TBB
std::execution
thread pool
```

再加：

```python
workers=
```

这个属于非 breaking optional argument，后面随时能加。

# 36. Public API 我最终建议冻结成这样

```python
# Single pair

bottleneck_distance(
    diagram_a,
    diagram_b,
) -> float


wasserstein_distance(
    diagram_a,
    diagram_b,
    *,
    order=1,
    internal_p=np.inf,
) -> float


# Prepared representation

prepare_diagram(
    diagram,
) -> PreparedDiagram


class PreparedDiagram:
    @property
    def n_points(self) -> int: ...

    @property
    def n_finite_points(self) -> int: ...

    def __len__(self) -> int: ...


# One-to-many

bottleneck_distances(
    query,
    diagrams,
    *,
    out=None,
) -> np.ndarray


wasserstein_distances(
    query,
    diagrams,
    *,
    order=1,
    internal_p=np.inf,
    out=None,
) -> np.ndarray


# Exact decision API

bottleneck_within(
    diagram_a,
    diagram_b,
    threshold,
) -> bool
```

这就是我认为你的 **v0.1 正式 API**。

# 38. 最终用户体验应该是这样的

普通单次：

```python
import tide

d = tide.bottleneck_distance(X, Y)
```

Wasserstein：

```python
w = tide.wasserstein_distance(
    X,
    Y,
    order=2,
    internal_p=2,
)
```

大量比较：

```python
query = tide.prepare_diagram(X)

distances = tide.bottleneck_distances(
    query,
    database,
)
```

筛选：

```python
if tide.bottleneck_within(X, Y, 0.05):
    ...
```

就是这些。

不要让 README 用户看到：

```python
CandidateStrategy.SORT_UNIQUE_CLIPPED
MatcherStrategy.MANDATORY_FLOW
AdjacencyStrategy.BITSET256
WassersteinMatcherStrategy.SPARSE_SAP
```

这些东西是你的**竞争优势**，但不是你的**用户接口**。

---

我认为你现在最合适的接口层级就是：

```text
                Tide public API
                       │
         ┌─────────────┴─────────────┐
         │                           │
 Bottleneck API               Wasserstein API
         │                           │
 single / prepared / batch    single / prepared / batch
         │                           │
         └─────────────┬─────────────┘
                       │
                 Native binding
                       │
                 Auto dispatcher
                       │
      ┌────────────────┼─────────────────┐
    small-N          medium-N          large-N
      │                │                 │
 bitset/SAP/...     adaptive/...    geometric/sparse/...
```

这个边界一旦定下来，你下一步就很机械了：

**先让 Wasserstein 补齐 `PreparedDiagram + one-to-many` → 冻结上面 7 个接口 → 写 pybind11 → pytest 做接口语义验收 → 再做 wheel。**

而且我尤其建议：**v0.1 宁可只正式支持 (W_{1,\infty}) 和 (W_{2,2})，也不要为了看起来完整而做一个半残的 generic Wasserstein。** 后者以后更容易形成 API 债务。

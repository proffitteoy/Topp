> 状态：historical proposal。本文保留当时的 Tide 临时代号和发布设想，不代表 Topp v0.1.0 的当前契约；当前发布文档见仓库根目录 README 与 `docs/` 用户文档。


你接下来应该按这个顺序做：

1. **把 Wasserstein 内核真正收口。** 现在远端文档明确还是 Phase 1/2，已有 `W1-L∞`、`W2-L2`、DSR、sweep 和 dense assignment，但 sparse weighted matching、component-wise matching、large-N dispatcher 仍然列在下一阶段。 你最近做的矩形 SAP、component 等实验如果还只在本地，应该先把赢家整合进 adaptive dispatcher，再跑和 Bottleneck 一样的随机顺序 median/p95、非对称规模、large-N、构造型最坏情况。也就是说，**不是每条优化路线都必须赢，而是每条有价值的路线都实验完，赢家进入默认路径，输家留下实验结论。**

2. **冻结公共数学 API。** 现在 C++ Wasserstein API 仍然直接暴露 `WassersteinCandidateStrategy`、`GraphStrategy`、`MatcherStrategy`、`ComponentStrategy` 等内部算法选择。 这些可以保留在 C++ debug API，但 Python 正式 API 不应该暴露。用户层我建议最终只有类似：
   `bottleneck_distance(X, Y)`、`wasserstein_distance(X, Y, order=1, internal_p=np.inf)`、`prepare(X)`、`bottleneck_distances(prepared, Ys)`、`wasserstein_distances(prepared, Ys, ...)`。
   其中你现在只支持 `(order=1,p=∞)` 和 `(order=2,p=2)`，那 v0.1 就明确限制这两个组合，不要为了“接口看起来通用”偷偷接受暂不支持的参数。

3. **把数值语义冻结。** 这是发布库比实验代码多出来的最重要部分。你自己的 `PROJECT_SCOPE.md` 其实已经把这些坑列出来了：`NaN`、`±inf`、birth > death、空 diagram、重复点、essential points、输入 dtype、非连续 NumPy array、exact 到底要求数学一致还是 bitwise 一致，目前都还没有最终契约。 这一步一定要在 Python binding 前定，否则以后就是 breaking change。

4. **做真正的 Python binding。** 目前 `CMakeLists.txt` 构建的是 `bottleneck_core STATIC`；所谓 C API 也只是 `tests/bottleneck_core_c_api.cpp` 的测试共享库，并不是 Python 扩展。 我建议直接用 **pybind11 + scikit-build-core**。scikit-build-core 官方文档就是 `pyproject.toml + CMake + pybind11 extension` 这条路径，而且与你现有 CMake 工程最契合。([Scikit Build Core][2]) 没必要先写 ctypes/CFFI 中间层。

5. **绑定层要专门做性能设计，而不是机械包一层。** NumPy `(n,2)` `float64` 最好走连续内存零拷贝路径；能安全转换的输入再复制。C++ 计算阶段释放 GIL；`PreparedDiagram` 做成真正的 Python 对象；one-to-many 必须一次进入 native 层，不要 Python `for` 循环反复调用 C++。你现在 Bottleneck C++ 已经有 prepared 和 native batch 设计，这个基础是对的。 Wasserstein 也应该补齐同级别 prepared/batch 接口。

6. **建立 Python 级正确性测试。** 不能只保留 C++ core tests。至少再有一层 `pytest`：NumPy 输入、list 输入、不同 dtype、non-contiguous view、空数组、异常输入、essential points、prepared/unprepared 一致、batch/single 一致。然后分别与固定版本 GUDHI/Hera/POT 之类 oracle 做差分。Wasserstein 当前文档自己也明确写着还没有固定版本外部 oracle 差分。

7. **做 Python API benchmark。** 这一步很重要，因为你这个库卖点就是性能。最终 README 里不能只写 C++ kernel 快多少，而应该同时给 `single-call`、`prepared one-to-many`、`large-N` 三种端到端 benchmark。你现有文档也已经意识到 kernel microbenchmark 不能替代 Python API 和批量吞吐结论。

8. **开始正式 packaging。** 你远端目前没有 `pyproject.toml`，所以这里还完全没开始。现代 Python packaging 应该把 build backend 和 project metadata 放到 `pyproject.toml`；PyPA 目前仍明确要求/推荐这套结构。([Python Packaging][3]) 这里要确定发行名、版本 `0.1.0`、Python 最低版本、NumPy dependency、license、authors、README、repository URL、classifiers 等。

9. **补 LICENSE、README、CHANGELOG 和 API 文档。** 当前 GitHub main 没有 `LICENSE`。发布开源库之前这个必须补。README 也要从现在的“实验日志型 README”重写成“用户型 README”：一句话定位 → installation → 30 秒 example → API → benchmark → supported metrics → compatibility → development。现在 README 仍明确写着 Python 外壳和 wheel 不处理，这显然不能作为首发 README。

10. **做 wheel CI，而不是让用户本地编译 C++。** 至少首发我会覆盖 CPython 3.10/3.11/3.12/3.13/3.14，以及 Windows x86-64、Linux manylinux x86-64、macOS x86-64/arm64；是否首发 Linux ARM64 可以后置。`cibuildwheel` 当前就专门负责跨 Python/Windows/Linux/macOS 构建和测试 binary wheels。([CIBuildWheel][4]) 对你这种 C++20 库尤其适合。

11. **处理 CPU ISA dispatch。** 你当前 CMake 在 MSVC x64 下单独用 `/arch:AVX2` 编译 AVX2 translation units。 发布通用 wheel 前必须验证：没有 AVX2 的 x86-64 CPU 是否绝不会执行这些指令、runtime feature detection 是否正确、baseline wheel 是否仍可运行。不要发布一个隐含要求 AVX2 的普通 `win_amd64` wheel。

12. **做 CI + release pipeline。** PR/commit 至少运行 C++ tests、Python tests、format/static checks 和几个 smoke build；tag `v0.1.0` 后单独构建 wheels + sdist，先 TestPyPI 安装测试，再正式 PyPI。PyPI 现在支持 GitHub Actions OIDC Trusted Publishing，不需要把长期 API token 塞进 GitHub Secrets，官方也推荐把发布职责隔离到单独的 `release.yml`。([PyPI 文档][5])

所以从你现在的位置看，路线其实很清楚：

**Wasserstein 算法收口 → Bottleneck/Wasserstein 公共 API 冻结 → Python binding → Python correctness/batch benchmark → packaging → wheels/CI → TestPyPI → v0.1.0。**

我不建议你在首发前继续无限优化算法。达到下面这个点就应该停止做内核研究并转产品化：

**Bottleneck dispatcher 已稳定 + Wasserstein sparse/dense dispatcher 已稳定 + 两者 correctness oracle 完整 + large-N 没有明显灾难性退化。**

之后哪怕还能再挖 10%–20%，都应该放到 `0.2/0.3`。否则这个项目会永远停留在 benchmark repository，而不会成为有人能 `pip install` 的库。

还有一个我认为现在就该定的架构：最终仓库可以变成：

```text
Tide/
├── pyproject.toml
├── CMakeLists.txt
├── LICENSE
├── README.md
├── CHANGELOG.md
├── src/
│   ├── cpp/                 # 现有 C++ core
│   └── <new_package_name>/
│       ├── __init__.py
│       ├── _api.py
│       └── _bindings.cpp
├── include/
├── tests/
│   ├── cpp/
│   └── python/
├── benchmarks/
├── docs/
└── .github/workflows/
    ├── ci.yml
    └── release.yml
```

也就是说，**你现在真正剩下的大块已经不是“再写什么算法”，而是“把这个优秀 C++ 内核变成一个可靠的 scientific Python product”。** 内核大致做完后，Python 包装、wheel、CI、数值契约和文档这部分通常还占整个发布工作的约三分之一，而且是决定别人敢不敢用的那三分之一。
